## Warnings

### [WARNING-1] Codebase uses `on_mouse_up` instead of `on_click` — deviates from Zed convention

**Files:**
- `src/ui/components/button.rs` (line 39)
- `src/ui/components/dropdown.rs` (lines 193, 260)
- `src/ui/components/slider.rs` (lines 163, 170)
- `src/ui/components/text_field.rs` (lines 662, 673, 680)
- `src/ui/tab_bar.rs` (line 186)
- `src/ui/bluetooth/bluetooth_page.rs` (line 103)
- `src/ui/bluetooth/device_row.rs` (lines 139, 151, 163, 185)
- `src/ui/dev_test_page.rs` (lines 119, 145, 153)

**What:** Every interactive element in the codebase uses `on_mouse_up(MouseButton::Left, ...)` for click handling. Zed's standard pattern is `on_click(cx.listener(...))` which uses `ClickEvent`.

**Why:** `on_mouse_up` fires when the mouse button is released, regardless of where the press originated. If a user presses the mouse on element A, drags to element B, and releases, `on_mouse_up` fires on B. `on_click` requires both press and release on the same element, providing proper click semantics. In Zed's workspace crate, `on_click` is used 61 times vs `on_mouse_up` only 2 times. The semantic difference matters for: (a) scan button — a drag from the tab bar could accidentally trigger a scan; (b) action buttons — dragging from one button to another could trigger the wrong action; (c) slider — `on_click` with `ClickEvent` provides button and modifier info more cleanly. Zed's `on_click` also includes a drag threshold so small mouse movements during a click don't cancel it.

**Fix:** Replace `on_mouse_up(MouseButton::Left, ...)` with `on_click(...)` across the codebase. The `on_click` API is available in gpui-unofficial 1.2.7. Example migration:

```rust
// Before (Bludio current)
.on_mouse_up(MouseButton::Left, move |_: &MouseUpEvent, _window, _cx| {
    on_click();
})

// After (Zed convention)
.on_click(move |_event: &ClickEvent, _window, _cx| {
    on_click();
})
```

For `window.listener_for()` patterns in RenderOnce elements:

```rust
// Before
.on_mouse_up(MouseButton::Left, window.listener_for(
    &entity,
    |this: &mut Dropdown, _, _, cx| { ... },
))

// After
.on_click(window.listener_for(
    &entity,
    |this: &mut Dropdown, _event: &ClickEvent, _, cx| { ... },
))
```

The slider's drag handling (`on_drag`, `on_drag_move`) should remain as-is — those are drag-specific APIs, not click replacements.

## Suggestions

### [SUGGESTION-1] Redundant `entity.clone()` inside `.map()` closure in `tab_bar.rs`

**File:** `src/ui/tab_bar.rs`
**Line:** 179
**What:** The outer scope captures `entity = cx.entity().clone()` at line 169, then the `.enumerate().map()` closure captures `entity` by reference and immediately clones it again: `let entity = entity.clone();`.
**Why:** The outer `entity` is already a clone; the inner `let entity = entity.clone()` is redundant. The closure could capture the outer `entity` directly since `.map()` takes ownership of the iterator.
**Fix:** Remove the inner clone and rebind:

```rust
// Before
let tab_buttons = self.tabs.iter().enumerate().map({
    let entity = entity.clone();
    move |(i, tab)| {
        // uses entity
    }
});

// After — the outer entity is already cloned, just move it into the closure
let tab_buttons = self.tabs.iter().enumerate().map(move |(i, tab)| {
    // uses entity directly (moved from outer scope)
});
```

Note: The outer `entity` variable is used after the `.map()` call at line 195 (for the indicator), so you'd need to clone it once at the outer scope and use `.clone()` only if the same entity is needed in multiple closures. Since there's only one closure, the inner clone is unnecessary.

### [SUGGESTION-2] `#[allow(dead_code)]` on icon functions lacks justification comment

**File:** `src/ui/icons.rs`
**Lines:** 26, 30, 34, 38, 42
**What:** `audio_output()`, `audio_input()`, `audio_card()`, and `text_field_test()` icon functions have `#[allow(dead_code)]` without comments explaining why they're kept. The `bluetooth()` function does NOT have this attribute (it's used in the scan button).
**Why:** These functions ARE used in the `TabBar` tab definitions in `app.rs`, so they're not actually dead code. The `#[allow(dead_code)]` attributes are unnecessary and should be removed. If they were added to suppress warnings during a refactor, they're now stale.
**Fix:** Remove the `#[allow(dead_code)]` annotations from all four icon functions. They are referenced in `app.rs` lines 67–83.

### [SUGGESTION-3] `#[allow(unused_imports)]` on theme re-exports may be stale

**File:** `src/ui/theme/mod.rs`
**Lines:** 10–12
**What:**
```rust
#[allow(unused_imports)]
pub(crate) use rose_pine_dawn_theme::rose_pine_dawn;
#[allow(unused_imports)]
pub(crate) use rose_pine_theme::rose_pine;
```
Both `rose_pine_dawn()` and `rose_pine()` are used in `dev_test_page.rs` (theme toggle buttons) and `main.rs` (initialization). The `#[allow(unused_imports)]` is stale.
**Why:** Unnecessary suppression attributes hide real issues. If these imports were unused, it would indicate dead code.
**Fix:** Remove both `#[allow(unused_imports)]` annotations.

### [SUGGESTION-4] `execute_device_action` returns `()` instead of `Result` — errors logged but invisible to caller

**File:** `src/bluetooth/device.rs`
**Lines:** 81–104
**What:** `execute_device_action` logs D-Bus errors via `eprintln!` but returns `()`. The caller in `app.rs` (line 287) can't distinguish success from failure.
**Why:** The UI shows success after every action because there's no error path. If a Connect or Disconnect fails, the user sees no feedback — the device just doesn't change state. The `eprintln!` output goes to the terminal, not the UI.
**Fix:** Change the return type to `Result<(), String>`:

```rust
pub(crate) async fn execute_device_action(
    adapter: &bluer::Adapter,
    addr: bluer::Address,
    action: DeviceRowAction,
) -> Result<(), String> {
    match action {
        DeviceRowAction::Connect => {
            let device = adapter.device(addr)
                .map_err(|e| format!("Device error: {e}"))?;
            device.connect().await
                .map_err(|e| format!("Connect failed: {e}"))
        }
        // ...
    }
}
```

The caller in `app.rs` could then surface the error through the Bluetooth state error field or a toast notification. This is a low-priority improvement since the current logging approach works for development.

### [POSITIVE-2] `RenderOnce` pattern consistently applied to complex components

**Files:** `src/ui/components/{dropdown,slider,text_field}.rs`
**What:** All three complex interactive components follow the same Entity → RenderOnce → IntoElement architecture. The Entity holds state + logic, the RenderOnce handles canvas/paint, and event dispatch uses `window.listener_for()`. The `#[derive(IntoElement)]` macro generates the `IntoElement` impl cleanly.
**Why this is good:** This matches GPUI's intended architecture. The pattern is documented in AGENTS.md and executed consistently. New components should follow this template.

### [POSITIVE-3] Shared constructor pattern with `RowParams` in `AudioDeviceRow`

**File:** `src/ui/audio/device_row.rs`
**What:** `new_sink` and `new_source` delegate to a private `new_impl(RowParams { ... })` constructor, avoiding duplication of ~100 lines of subscription wiring, slider setup, and text field creation.
**Why this is good:** The `RowParams` struct cleanly bundles variant-specific data (profile info vs. none, card index vs. none). New constructors would be trivial to add. This is the documented AGENTS.md pattern and is executed correctly.

### [POSITIVE-4] Volume command dedup prevents PA thread backlog

**File:** `src/audio/pulse.rs` (lines ~250–270)
**What:** The PA command loop uses a `HashMap<(DeviceKind, u32), AudioCommand>` for volume commands, keeping only the last one per device. Non-volume commands (mute, default, profile) are processed immediately.
**Why this is good:** This is a thoughtful optimization. During rapid slider dragging, the UI sends many `SetVolume` commands. Without dedup, the PA thread would execute every intermediate value, causing lag. The HashMap ensures only the final value is applied. This pattern should be documented in AGENTS.md as a PA backend convention.

### [POSITIVE-5] Complete IME and text editing support in `TextField`

**File:** `src/ui/components/text_field.rs`
**What:** The `TextField` implements the full `EntityInputHandler` trait with UTF-16 offset conversion, IME support, clipboard operations, grapheme-cluster-aware cursor movement, word selection on double-click, and epoch-based cursor blink management.
**Why this is good:** This is a production-quality text input component. The `EntityInputHandler` impl correctly handles the GPUI IME protocol. The cursor blink epoch counter (matching Zed's pattern) prevents stale timer callbacks during rapid interaction. This component could be extracted into a reusable library.
