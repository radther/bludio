# Codebase Audit Report

## Summary

0 critical, 2 warnings, 3 suggestions. The subsystem-resilience change is well-structured — the `SubsystemStatus` enum cleanly replaces scattered booleans, the reconnect loops follow consistent patterns, and the shared `AudioConnection` / `connect_bluetooth` helpers eliminate duplication. The warnings concern silent error swallowing on channel sends and an orphaned comment referencing a removed feature.

## Warnings

### [WARNING-1] Silent `let _ =` on channel sends swallows potential errors

**Files:**
- `src/bluetooth/monitor.rs` lines 45–49 (adapter listener)
- `src/bluetooth/monitor.rs` line 75 (per-device listener)

**What:** `let _ = adapter_tx.unbounded_send(...)` and `let _ = tx.unbounded_send(...)` discard the `Result` from `unbounded_send`. If the receiver is dropped (e.g., the monitor task exits), these silently fail.

**Why:** During normal operation these will never fail — the receiver lives as long as the monitor. But if the receiver drops unexpectedly (bug, race), the adapter listener would silently stop reporting `Powered` changes with no log output, making rfkill detection failures invisible.

**Fix:** Add `eprintln!` on the error path, matching the pattern used elsewhere in the codebase (e.g., discovery.rs):
```rust
if let Err(_) = tx.unbounded_send(MonitorEvent::AdapterPoweredOn) {
    eprintln!("[monitor] Adapter event send failed, receiver dropped");
    return;
}
```

### [WARNING-2] Stale comment references removed `NameOwnerChanged` watcher

**File:** `src/bluetooth/monitor.rs` line 88
**What:** Comment says "The adapter listener will catch Powered changes or the NameOwnerChanged watcher will catch BlueZ restarts." The `NameOwnerChanged` watcher was removed during implementation — the comment is misleading.

**Fix:** Update to: "The adapter listener will catch Powered changes. BlueZ restarts are detected by the reconnect retry loop (init failure → retry)."

## Suggestions

### [SUGGESTION-1] `AudioConnection::spawn()` creates channels that may never be used on failure

**File:** `src/app.rs` `spawn_audio_reconnect`

**What:** On each retry iteration, `AudioConnection::spawn()` creates a PA thread and channels. If the wakeup timeout fails, the spawned PA thread and its sender end of `state_rx` are dropped, but the PA thread itself continues running until it detects the dropped `cmd_rx` or errors out.

**Why:** This is functionally correct — the PA thread will exit when it tries to send state and finds the receiver dropped, or when it tries to receive a command and finds the sender dropped. But there's a brief window where an orphaned PA thread exists.

**Impact:** Negligible — the thread exits within one mainloop iteration (~ms). No resource leak.

**Fix:** No code change needed. Document the behavior with a comment in `AudioConnection::spawn()` noting that the caller is responsible for keeping the receivers alive or the thread will self-terminate.

### [SUGGESTION-2] `Cargo fmt` not applied to `connect_bluetooth` signature

**File:** `src/app.rs` line 338

**What:** `cargo fmt --check` reports a line-length difference on the `connect_bluetooth` function signature.

**Fix:** Run `cargo fmt`.

### [SUGGESTION-3] Row clearing on non-Connected status could be a single helper

**Files:** `src/ui/audio/audio_page.rs`, `src/ui/audio/configuration_page.rs`, `src/ui/bluetooth/bluetooth_page.rs`

**What:** All three pages have identical logic: `if status != Connected { self.rows.clear(); return; }` at the top of their sync methods.

**Why:** Minor duplication. Not harmful, but a shared `clear_if_disconnected(&mut self)` trait or method on each page would make the pattern explicit.

**Fix:** Low priority. Consider extracting if more pages are added.

## Notes

### [NOTE-1] Recursive spawn pattern in reconnect flows

Both `spawn_bluetooth_init` → `reconnect_bluetooth` → `spawn_bluetooth_init` and `spawn_audio_state_loop` → `spawn_audio_reconnect` → `spawn_audio_state_loop` form recursive spawn chains. Each task exits before spawning the next, so there's no stack growth — the GPUI executor handles each as an independent task. This is functionally correct but worth noting as an unconventional pattern. If the reconnect loop ever fails to exit the outer task, the chain could grow. The current implementation handles this correctly.

### [NOTE-2] Adapter listener survives monitor task exit

When `spawn_bluetooth_init`'s event loop exits (e.g., after `AdapterPoweredOff`), the `monitor_tx` channel sender and `monitor_rx` receiver both stay alive — `monitor_rx` is captured by the `reconnect_bluetooth` spawned task. The adapter listener (`_adapter_listener`) continues running and can still send `Powered` events through the channel. This is correct and intentional, but the lifetime coupling is non-obvious.

### [NOTE-3] `connect_bluetooth` unwrap on session is safe but lacks context

**File:** `src/app.rs` line 341

`state.session.as_ref().unwrap()` is safe because `BluetoothState::new()` only returns `Ok` after successfully creating the session. However, if `BluetoothState::new()` is ever refactored to return `Ok` before session creation, this would panic. A comment explaining the invariant would be defensive.

## Positive Findings

- **`SubsystemStatus` enum is excellent.** Replacing `connected: bool` + `error: Option<String>` + `initialized: bool` with a single enum eliminates impossible states and makes rendering a clean `match`. The `#[default]` attribute on `Connecting` is idiomatic.

- **`AudioConnection::spawn()` and `connect_bluetooth()` helpers.** Extracting shared connection logic eliminates the exact duplication between init and reconnect paths. This follows the project's documented "shared constructors" pattern from AGENTS.md.

- **Context health check ordering in `pulse.rs`.** Moving the `ContextState::Failed | Terminated` check before `build_audio_state` prevents the null-pointer panic from introspecting a dead PA context. The comment explaining why the check must come first is clear and prevents future regressions.

- **Retry loops with consistent 3s interval.** Both audio and Bluetooth reconnect use the same pattern: 1s initial delay, 3s retry interval. This makes the behavior predictable and easy to reason about.

- **Monitor `MonitorEvent` enum.** The typed enum (`DeviceChanged`, `AdapterPoweredOff`, `AdapterPoweredOn`) is cleaner than the previous raw `bluer::Address` channel. It makes the event handling in `spawn_bluetooth_init` self-documenting.
